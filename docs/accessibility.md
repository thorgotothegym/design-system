# Accessibility

This is an audit of the 11 components of `@aleixvidal/ui` and the realistic form pattern against WCAG 2.2 level AA, done on 2026-11-02. It records what was checked, how, what was found, and what is still to verify.

**This is not a certification and not a conformance claim.** No screen reader has been run yet. A conformance claim needs the manual pass in the [checklist below](#manual-verification-checklist), and the findings marked open need fixing first. The raw evidence (keyboard transcripts, accessibility tree extracts, measurements) is in [accessibility/evidence.md](accessibility/evidence.md), with the screenshots it cites.

## Scope and method

- **What:** Input, Textarea, Field, Checkbox, Switch, RadioGroup, Select, Slider, TagInput, OtpInput, DatePicker, and the realistic form (`Patterns/Realistic form`), in the dark and light themes.
- **How:** the built Storybook (`STORYBOOK_PLAY_DELAY=0`), driven by Playwright with real keyboard and pointer events (each key held 80 ms, as a person presses it). The audit reads what assistive technology reads: the accessibility tree (aria snapshots), accessible names, states and descriptions, focus, computed styles and box sizes. It never relies on class names.
- **Browsers:** Playwright's Chromium 1248 for everything; Firefox 157.0 and WebKit 27.2 for the cross-browser checks listed below. One browser at a time.
- **Re-running it:** build with `STORYBOOK_PLAY_DELAY=0 pnpm exec turbo run build --filter=@aleixvidal/storybook --force`, then run `node scripts/a11y-audit.mts all` (or one check: `keyboard`, `names`, `target`, `reflow`, `modes`, `known`, `input-purpose`, `otp`, `lang`, `cross-browser`, `ssr`). It writes raw results to `a11y-audit-results.json` and the screenshots it takes to `docs/accessibility/`. It is not part of CI.
- **Already automated in CI** (unchanged by this audit): axe on every story in both themes (`a11y` job, Storybook test runner), axe in the unit tests of every component (jsdom), the token contrast gate, and Lighthouse Accessibility on three pages.

## Summary

- **Keyboard:** every component works with the keys of its WAI-ARIA Authoring Practices pattern, with no keyboard trap and a visible, unobscured focus indicator on every stop, in both themes. One deviation, documented: Home and End on a range Slider move the first and last thumb, not the focused one (A11Y-05, Radix behavior).
- **Names, roles, states:** every control has a name that contains its visible label (2.5.3). `required`, `invalid`, `disabled`, read-only, checked, expanded and value text are exposed, and error messages are part of each control's description.
- **Target size, reflow, text:** every target passes 2.5.8 (the 20 px checkbox and radio boxes and the date segments pass by spacing). There is no horizontal scroll or clipped text at 320 px, with text at 200 %, or with the WCAG text-spacing overrides.
- **Forced colors** (Windows contrast themes) was where the real problems were. Several states were drawn only with a background fill, which forced colors removes: the Switch thumb, the selected radio dot, the selected and today days of the calendar, and the Slider range. The OtpInput also showed its hidden input's text over the boxes (A11Y-01 to A11Y-04). These, and the invalid and disabled states and two icons that had the same kind of defect (A11Y-15 to A11Y-17), are fixed in #49 and checked in CI by emulation (see [Forced colors](#forced-colors)). A real Windows contrast theme has not been tested.
- **Not verified yet:** screen reader output (VoiceOver, NVDA), real Safari and Firefox releases, and browser zoom at 400 % (emulated here with a 320 px viewport).

### A11Y-11: a partly filled date (documented)

What the user sees: the field shows "3 / dd / 2025", and nothing changes until the form is submitted; the realistic form then says "Enter a complete date (month, day and year)".

Decision (#50): the DatePicker keeps reporting `null` for a partial date, so a form never submits half a date, and it does **not** mark itself invalid while the person is typing: an error that appears after the first digit would be announced mid-entry. The form's `required` rule handles it with one message for an empty and an incomplete date, shown on blur or submit in `Field.Error`; the field then gets the danger border and `aria-invalid` through `Field`, and the empty parts keep their placeholder, so it is clear which part is missing. This is documented in the DatePicker JSDoc and story, with the realistic form as the example. The earlier idea of exposing "incomplete" separately (`data-incomplete`, a callback) is not adopted: no consumer needs it, and it would add API surface.

## Criteria not applicable

- **1.2.x (time-based media):** no audio or video.
- **1.3.4 Orientation:** nothing locks the orientation.
- **1.4.13 Content on hover or focus:** nothing appears on hover or focus (no tooltips); popups open on a click or a key and close with Escape.
- **2.1.4 Character key shortcuts:** the Select typeahead reacts to single characters only while its trigger has focus, which the criterion allows.
- **2.2.x Enough time:** no time limits. The "Submitting" story waits forever on purpose; it is a story, not a timeout.
- **2.3.1 Three flashes:** nothing flashes (the theme switch was measured in #34).
- **2.5.1 Pointer gestures, 2.5.4 Motion actuation:** no path or multi-point gestures, no motion input. Dragging a Slider thumb has single-click and keyboard alternatives (2.5.7, verified).
- **3.2.6 Consistent help, 3.3.7 Redundant entry:** a single-page form with no help mechanism and no information asked twice.
- **3.3.4 Error prevention (legal, financial, data):** the realistic form submits to a demo, with no legal or financial commitment.

## Observations about the published site

These are about the Storybook site at design.aleixvidal.dev, not the library:

- **3.1.1 Language of page:** both pages, the manager (`index.html`) and the preview (`iframe.html`), declare `lang="en"`.
- **3.1.2 Language of parts:** see A11Y-13, fixed in #50: a DatePicker in another language declares it.
- **Safari and WebKit Tab order:** by default, Safari tabs only to text fields; the Select trigger, switches, checkboxes and buttons are reached with Option+Tab, or with the setting "Press Tab to highlight each item". The components are reachable either way; this is the browser's setting.

## Forced colors

Windows contrast themes (and the forced colors of Firefox and Edge) replace the page's colors with the user's: text and borders become `CanvasText`, and every background becomes `Canvas`. A state drawn only by a background fill disappears. Components handle it with `forced-colors:` variants and CSS system colors (AGENTS.md section 6):

| State                     | Under forced colors                                                                                                                                                                            |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Switch on / off           | on: `Highlight` track and `HighlightText` thumb on the right; off: empty track and `CanvasText` thumb on the left (fill and position)                                                          |
| Radio selected            | a `Highlight` dot; unselected: no dot                                                                                                                                                          |
| Calendar selected day     | `Highlight` fill and `HighlightText` number, also after focus moves away (the cell opts out with `forced-color-adjust: none`, so Chromium does not paint a `Canvas` backplate over the number) |
| Calendar today            | a `CanvasText` dot, `HighlightText` on the selected day                                                                                                                                        |
| Slider value              | the filled part in `Highlight`, the rest empty                                                                                                                                                 |
| OtpInput                  | the hidden input keeps its text transparent (`forced-color-adjust: none`); the caret is `CanvasText`                                                                                           |
| Invalid                   | a dashed border (same width, so nothing moves)                                                                                                                                                 |
| Disabled                  | a `GrayText` border and `GrayText` text, as native controls                                                                                                                                    |
| Focus, highlighted option | unchanged: outlines become `CanvasText`, which forced colors keeps                                                                                                                             |

**Automated check.** The `storybook-forced-colors` project in `apps/storybook/vitest.config.ts` runs the hidden stories in `apps/storybook/src/foundations/forced-colors.stories.tsx` in Chromium with `forcedColors: 'active'`, as part of `pnpm test:storybook` (the `a11y` CI job). They assert computed styles, not pixels: the switch thumb, the on track, the radio dot, the slider fill, the selected day and the today dot are not `Canvas`; the selected day's number differs from its fill and its focus ring is `CanvasText`; the OtpInput's input is transparent with `forced-color-adjust: none`; invalid is dashed, disabled has a `GrayText` border and text, and the Select chevron is `CanvasText`. With the fixes reverted, both stories fail. They are excluded from Chromatic (it does not emulate forced colors) and from the dark and light projects. axe's `color-contrast` is off in them only: under forced colors it mixes the token color of the text with the forced `Canvas` and reports contrasts that are not painted.

**Checking by hand** (Chrome or Edge): open DevTools, then the Command Menu (Cmd+Shift+P on macOS, Ctrl+Shift+P on Windows), run "Show Rendering", and in the Rendering tab set "Emulate CSS media feature forced-colors" to `active`. Then go through the stories of each component: every state in the table above must be visible without relying on a color difference. On Windows, use a real theme instead: Settings > Accessibility > Contrast themes, pick one (for example Night sky or Desert), and use Edge or Chrome.

## Known limitations of this audit

- No screen reader has been run: the expected output in the checklist is what the accessibility tree contains, not what a screen reader says.
- Firefox and WebKit are Playwright's builds (Firefox 157.0, WebKit 27.2), and only the stories listed under cross-browser were run in them. Released Safari and Firefox are pending.
- Zoom at 400 % is emulated by a 320 px viewport, which is what 1.4.10 measures; real browser zoom was not run. Text at 200 % was tested by doubling the root font size, which scales every rem-based size.
- Forced colors was emulated in Chromium (`forcedColors: 'active'`), not on Windows with a real contrast theme. The fixes of #49 were verified the same way: by emulation, in Chromium only. A real Windows contrast theme (and Firefox's own forced colors) has not been tested; see the [manual step](#forced-colors-pass).
- Target sizes were measured on the default size of each control. The `sm` sizes were not measured.
